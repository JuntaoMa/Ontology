EXECUTIVE SUMMARY

核心判断

本体不会取代向量检索或 GraphRAG；更可行的方向是把本体作为检索与推理的“语义控制平面”，让 Agent 按问题类型动态组合关键词、向量、图、规则和原始证据。

RAG 的本质

把外部非参数记忆接入生成。其主流工程路线已从单次向量 Top‑K，演进为混合召回、重排、查询改写、分层索引、反馈与评估闭环。

GraphRAG 的增量

显式保存实体与关系，利用社区、路径、中心性或扩散算法支持多跳与全局问题。但“有边”并不自动带来类型、公理、约束和逻辑蕴含。

Ontology 的机会

用规范概念、同义词、类型层级、关系约束、公理与治理元数据，缩小自然语言到真实业务对象之间的解释空间，并把答案验证从“模型觉得合理”推进到“机器可检查”。

建议定位：优先称为 Ontology-Augmented Retrieval & Generation（OARG），而不是新的单一检索算法。其价值来自：意图语义化 → 受约束检索计划 → 可解释推理 → 证据回链 → 约束验证。
EVOLUTION

技术演进与当前方向

2020–2022 · 基础 RAG稠密检索器连接参数记忆与外部文档；重点是开放域 QA、知识更新和来源可追溯。
2023–2024 · Advanced RAG混合检索、reranker、HyDE/查询扩展、父子块、上下文压缩、自反思与端到端评估成为主流工程组件。
2024–2025 · GraphRAGMicrosoft GraphRAG、LightRAG、HippoRAG 等分别探索社区摘要、双层图检索、Personalized PageRank 与关联记忆。
2025–2026 · Agentic / Structured RAGAgent 负责拆解、路由、迭代检索、工具调用与验证；文本、表格、图、代码、数据库和长期记忆统一进入检索编排。

现在最重要的六条方向

1. 混合与多阶段检索

BM25 + dense + metadata filter + reranker，追求召回与精度的可控平衡。

2. 结构化/多模态知识

从纯文本扩展到表格、关系库、图、图片与时序数据；STaRK 类基准揭示半结构检索仍然困难。

3. Agentic RAG

检索从固定流水线变为计划—执行—观察—修正循环，并加入答案可回答性判断。

4. 长期记忆

情节、实体、关系和程序性记忆分层；图扩散与时间/重要性信号结合。

5. 小模型与成本治理

路由、抽取、重排、判分使用专用模型；只在复杂推理时调用强模型。

6. 可观测与细粒度评估

把错误定位到意图、召回、重排、上下文、推理或生成，而非只看最终答案分数。

关键辨析：Embedding 不是“没有语义”，它学习的是分布式、概率性的语义；GraphRAG 也不是“有图就有语义”，多数系统的图是 LLM 抽取的事实网络，而非具有模型论语义的本体。Ontology 的独特价值是显式、共享、可计算的意义与约束。

ONTOLOGY LENS

Agent 能力提升后，本体为何更有价值

自然语言 → 领域意图

Agent 可把“欧洲高风险供应商”映射成类、属性、地理范围、风险口径和有效时间，先澄清语义再检索，而不是直接押注一个 embedding。

规划而非单路召回

本体提供可调用的数据能力目录：哪些概念在哪个系统、可用何种关系、哪些字段敏感、哪些规则可推导。Agent 据此生成 SPARQL、SQL、图遍历和向量检索的组合计划。

生成后机器验证

SHACL/规则可检查类型、基数、枚举、时间范围和互斥条件；OWL/规则推理可显式化隐含事实。验证失败时，Agent 能针对缺失证据再检索。

最有价值的场景

制造 BOM/设备谱系医药术语与编码金融产品与合规主数据治理数据资产语义层复杂产品配置

这些场景共同具有：术语歧义代价高、关系/规则比主题相似更重要、需要跨源对齐，并要求审计“为什么得到这个答案”。2025 年的 OntologyRAG 已在生物医学本体编码映射中展示了“本体图 + LLM + 可解释邻近性”的具体方向，但目前证据仍以单领域、小规模研究为主，不足以证明其普适优势。

REFERENCE ARCHITECTURE

推荐：语义控制平面 + 多路检索数据平面

1. 语义入口问题规范化、实体链接、术语消歧、时间/单位/权限识别；输出结构化 Semantic IR，而不是直接生成查询。
2. 本体控制平面TBox（概念/关系/公理）+ SHACL（质量约束）+ 词汇表/同义词 + 数据源映射 + 权限/血缘/时效元数据。
3. Agent 检索规划器按意图分类选择：BM25、向量、SQL/SPARQL、Cypher/图扩散、规则推理；生成成本预算与停止条件。
4. 多路候选生成文本召回处理开放表达；图检索处理关系；形式查询处理精确条件；ontology expansion 做同义/上下位概念扩展。
5. 语义融合与重排将 lexical、dense、graph、type-fit、rule-fit、freshness、authority 等分数融合；硬约束先过滤，软语义再排序。
6. 证据包与推理返回最小充分证据：原始片段/记录 + 实体 ID + 路径 + 推导依据 + 时间/来源；LLM 只在证据包内综合。
7. 验证与治理逐声明引用、SHACL/规则校验、冲突检测、答案置信与拒答；全链路记录 ontology 版本、查询计划和证据版本。

建议的检索评分

Score = α·lexical + β·dense + γ·graph + δ·typeFit + ε·ruleFit + ζ·authority + η·freshness
不要固定一组全局权重。由问题类型、领域风险和候选规模决定；类型、权限与合规条件应作为硬门控，不应被相似度“抵消”。
TECHNICAL NORTH STAR

OAG 技术目标：四个可独立演进的核心模块

Agent 负责计划、调用和循环控制；OAG 的竞争力应沉淀在 Agent 之下。即使替换 Agent 框架，语义编译、检索、推理和证明能力仍然成立。

01 · Semantic Compiler

语义编译器

目的：把自然语言问题转换为经过本体约束、可类型检查的 Semantic IR，而不是直接生成某一种数据库查询。

核心能力：识别实体、类型、关系方向、时间、单位、否定、数量、聚合和歧义候选；在执行前发现不合法或信息不足的问题。

价值：把“模型理解”变成可检查的语义程序，为跨数据源执行、组合泛化和精确消歧建立统一入口。

02 · Semantic Retrieval Runtime

语义检索运行时

目的：把 Semantic IR 编译为 BM25、向量、GraphRAG、SQL、SPARQL、时序与规则查询的组合执行计划。

核心能力：区分硬约束与软相关性，执行类型约束召回、方向敏感图扩展、本体查询扩展、多路候选融合与成本/覆盖感知路由。

价值：保留朴素 RAG 的开放召回能力，同时利用本体降低类型混淆、关系误判和过度扩展。

03 · Neuro-symbolic Reasoner

神经符号推理器

目的：在检索事实之上执行确定性推导、约束检查、时间/因果分析和不确定条件下的诊断。

核心能力：组合 OWL/RL、Datalog、业务规则、时间逻辑与溯因推理；寻找能覆盖观测、违反最少约束的最小根因集合。

价值：把 GraphRAG 的“相关路径”提升为受语义约束的推导与诊断，支持制造故障和通信网络根因分析等高价值任务。

04 · Proof Engine

证明与证据引擎

目的：为答案中的每个声明生成可机器验证、可回溯的最小充分证据图。

核心能力：连接原始事实、文档条款、拓扑路径、规则、公理、时间和数据版本；明确区分直接事实、逻辑推导、统计推测与 LLM 判断。

价值：将解释从事后生成的理由升级为 proof-carrying answer，支撑幻觉控制、审计、拒答和 Agent 自我修正。

技术边界判断：如果更换 Agent 后上述四个模块仍能保持语义精度、检索效果、推理能力和证明有效性，它们就是 OAG 的技术资产；Agent 则是消费这些能力的上层编排器。
DELIVERY ROADMAP

可行落地路线：先证明增量，再扩大本体

Phase 0 · 2–3 周
选 30–80 个高价值 competency questions，建立普通混合 RAG 基线；标注答案、证据、实体、关系和失败类型。
Phase 1 · 4–6 周
构建轻量领域词汇表与核心 ontology（优先 SKOS/RDFS + 少量 OWL），完成实体 ID、同义词、上下位和关键关系；不追求“大而全”。
Phase 2 · 4–8 周
上线 ontology-aware query expansion、类型过滤和结构化查询路由；与 baseline 做逐题消融：vector → hybrid → graph → ontology。
Phase 3 · 6–10 周
加入 Agent 规划、SHACL 验证、规则推理、证据证明链和拒答；针对高风险问题设置 deterministic path。
Phase 4 · 持续
把失败案例转为 ontology/映射/评测资产；引入版本治理、变更影响分析与人审队列，形成语义 DevOps。

PoC 的三个首选实验

A. 类型约束召回

选择名称高度相似但类型不同的数据，验证 ontology type filter 对 Precision@K 和错误答案率的提升。

B. 多跳规则问答

设计必须经 2–4 跳关系与一条规则才能回答的问题，对比向量、GraphRAG、Ontology+Agent。

C. 跨源语义对齐

同一概念在文档、数据库和业务系统中名称不同，测实体链接、查询成功率与来源审计完整性。

本体债务

过度建模导致交付缓慢。以问题驱动的 competency questions 控制边界，用模块化 ontology 和版本契约。

开放世界与业务闭世界冲突

OWL 中“未声明”通常不等于“为假”。业务校验使用 SHACL/规则表达闭世界约束，避免混用语义。

LLM 抽图污染

LLM 生成的三元组必须有 provenance、置信度和审核策略；TBox 变更与 ABox 写入权限分离。

推理成本

选择 OWL 2 EL/RL/QL 等适合任务的 profile，预计算稳定蕴含；仅对候选子图做查询时推理。

基准失真

最终 QA 分数掩盖组件错误。采用分层指标、消融实验和真实高相似/冗余语料，并保留人工金标准。

Agent 不确定性

规划器可生成错误查询。限制工具 schema、查询模板与预算；高风险链路采用确定性工作流并验证结果。

DECISION

最终建议

值得投入，但应把目标定义为“提高高价值语义任务的可验证正确率”，而不是“把全部企业知识做成本体”。

  1. 保留成熟的 hybrid RAG 作为广覆盖底座；GraphRAG 用于关系密集、多跳和全局分析；Ontology 用作精确语义、约束、路由和治理。
  2. 从轻量 SKOS/RDFS + SHACL 开始，只在确有推理收益时引入 OWL 公理与规则；本体复杂度应由 competency questions 驱动。
  3. 让 Agent 消费 ontology，而不是让 Agent 随意改 ontology。模型可提出候选概念、映射和规则，但生产发布必须经过验证与治理。
  4. 建立“证据优先”协议：所有推导节点回链到原始事实和来源，形式推理结果与 LLM 推测明确分栏。
  5. 是否扩大投入，由消融结果决定：若 ontology 路线未在类型歧义、多跳规则、跨源对齐三个核心实验上显著优于 hybrid/GraphRAG，就缩小范围。

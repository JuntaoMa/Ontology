PAPER DEEP DIVE · KEIR@ECIR 2025

OntologyRAG 到底做了什么？

对 Feng et al.《OntologyRAG: Better and Faster Biomedical Code Mapping》的数据、系统、实验结果、证据强度与 OAG 启示进行逐层拆解。

更新：2026-07-14原文：arXiv:2502.18992 v1范围：假设本体及映射数据已可用，不讨论本体治理
一句话判断任务数据方案结果局限OAG 启示资料
BOTTOM LINE

先给结论

这是一套“本体映射候选的结构化取回 + LLM 语义分级”系统，不是形式逻辑推理型 OAG。

它的关键贡献不是从本体中推导新事实，也不是用图算法发现映射，而是：把已有 ontology/code mapping 放入 RDF 图；让 LLM 把自然语言问题翻译为 SPARQL；取回候选映射；再让 LLM 根据两个标签的语义接近程度分成 A/B/C，并生成解释，帮助专家优先处理歧义案例。

论文有价值地证明了“先用结构化知识限定候选，再让通用 LLM 做局部语义判断”远比要求 LLM 凭参数记忆直接报代码可靠。但论文没有端到端证明检索质量、专家节省工时、映射最终正确率或跨本体泛化，因此标题中的 “Better and Faster” 仍主要是合理推断，而非被完整实验验证的结论。

PROBLEM

研究任务：不是普通问答，而是生物医学编码映射精炼

输入问题

不同疾病分类/医学术语体系中，同一或相近概念使用不同 code 与 label。已有自动流程会产生“未精炼映射候选”，专家必须判断哪些是等价、部分相关或冲突。

典型问题：给定 ICD-10-WHO code N17，列出 ICD-11-WHO 映射，并判断每个候选与 “Acute renal failure” 的接近程度。

输出目标

系统返回候选 code、label、映射等级和自然语言理由：

A 完全一致B 相关但不确定C 部分冲突

注意：A/B/C 是作者为人工审核工作流设计的三档语义接近度，不是 OWL/SKOS 标准 mapping relation，也不是概率校准后的置信度。

真正的系统边界：候选映射已经存在于图中。OntologyRAG 负责访问、呈现和复核候选；它没有评估“从零发现所有正确跨本体映射”的能力。
DATA

两套 500 条数据，回答的是两个不同问题

500ICD-9-CM → 2018 ICD-10-CM 映射样本

数据集 A：直接映射基线

来自作者整理的 2018 映射 gold set。每条含一个源 code 与一个或多个目标 code，用于测试 LLM 不访问 KG 时能否直接输出映射。

500疾病描述对 + A/B/C 人工修订标签

数据集 B：接近度分类

先由 GPT-3.5-Turbo 基于常见疾病分类体系生成描述对并预测等级，再由领域专家人工修订；用于比较模型、提示策略和 temperature。

1,000总评测记录，但不是同一个端到端测试集

不可混为一个结果

数据集 A 证明闭卷直接报代码很难；数据集 B 证明给定两个 label 后三分类可做。两者之间没有共同样本链路，不能据此计算完整流水线准确率。

对公开仓库数据的复核

复核项实际观察解释
映射数据集 A500 个不同源 code；371 条单目标，129 条多目标；最多 7 个目标。26% 样本涉及一对多，符合 GEM 映射的复杂性；论文的评分对漏掉目标扣分，但不惩罚额外目标。
等级数据集 B 分布A=108（21.6%）、B=172（34.4%）、C=220（44.0%）。类别不均衡；只看 accuracy 会受到多数类影响，论文因此额外报告各类 precision，但没有 recall/F1。
few-shot 示例标准 few-shot 16 条；增强/CoT 21 条；与 500 条 gold set 无完全相同的输入对。未发现“示例直接重复测试样本”的泄漏，但描述模板和生成模型可能带来分布同源偏差。
图数据仓库只提供一个压缩为单行的 ICD-10-CM→ICD-11 2024 TTL 示例。足以演示，但无法完整复现论文涉及的所有专有 ontology/mapping 场景；源文件转换器也未公开。

数据来源与构造细节

论文描述的 ICD-9-CM diagnosis/procedure code 与 label 来自 CMS，ICD-10-CM 来自 CDC，ICD-9-CM→ICD-10-CM 的 GEM 文件来自 CMS。不同来源经定制 ETL 转换为 RDF，并保留 code、label、映射方向和相关 flags。公开仓库则提供 gold Excel、结果文件、prompt、运行脚本及一个 ICD-10-CM→ICD-11 图样例。

gold 的限制：数据集 B 是“模型生成候选 + 专家修订”，不是从真实专家审核队列自然抽样；论文未报告专家人数、专业资历、标注指南执行过程、独立双标、冲突仲裁或 inter-annotator agreement。因此它更适合原型比较，不足以作为成熟临床语义一致性基准。
METHOD

系统方案：三段流水线，LLM 调用至少三类

1. ETL异构 ontology 与 mapping 文件转 RDF
2. Index载入 Oxigraph 图数据库
3. NL2SPARQLNLQ + schema + graph list + few-shot
4. Validate执行查询验证语法与图中术语
5. RetrieveCONSTRUCT 取回 code/label/mapping 子图
6. Classify逐 code pair 预测 A/B/C
7. Explain按已定等级生成理由并汇总

1. Indexing：RDF 是统一数据接口

作者为每个来源编写定制 extraction/transformer，把 code、label、层级、关系和未精炼映射转换为 RDF 三元组，再装入基于 RocksDB 的 Oxigraph。这里“ontology enhanced”的主要载体是 RDF 图及其命名图/metadata；论文没有展示 OWL reasoner、description logic entailment、SHACL 或规则引擎参与答案生成。

2. Retrieval：自然语言先被编译成 SPARQL

NL2SPARQL prompt 包含任务约束、可用 graph source 列表、schema 和示例，要求生成 CONSTRUCT 查询。程序实际执行查询作为自校验：若语法无效或查询无法运行，则继续请求模型，直到得到可执行 SPARQL。GPT-3.5/GPT-4 能直接输出查询；Llama-3-8B 常混入对话文本，代码用字符串截取做后处理。

3. Reasoning & Summarization：先分类，再按分类解释

对每个源/目标 label pair，第一次调用 LLM 只预测 A/B/C；第二次把该预测作为条件，让 LLM 生成理由；最后把问题、候选、等级和理由再交给 LLM 汇总。这个拆分避免“自由推理”直接改变分类格式，但也意味着理由是对既定结论的事后合理化，不能被视为独立证明。

与典型向量 RAG 的区别：这里没有 embedding Top-K。召回集合由图中已有 mapping edge 和 SPARQL 精确选择决定；LLM 的语义作用主要发生在 NL2SPARQL 与 label-pair 分级阶段。
RESULTS

实验结果：最强证据在“闭卷很差、给定候选后可分类”

实验 1：LLM 直接做 ICD 映射，全部低于 10%

模型zero-shot mean accuracy解读
GPT-3.5-Turbo0.27 ± 0.21%几乎不能凭参数记忆完成版本特定映射。
GPT-48.38 ± 1.09%四者最佳，但远不足以直接用于映射。
Meta-Llama-3-8B-Instruct4.67 ± 1.70%优于 GPT-3.5，但仍很低。
Flan-T5-XXL0.00 ± 0.00%未命中 gold 目标。

评分细节很重要：若 gold 有多个目标，命中其中一部分按比例得分；模型多报额外 code 不扣分。因此该“accuracy”更接近每个源 code 的 gold-target recall，再做宏平均，并不衡量预测 precision。

实验 2：NL2SPARQL 能用，但评估非常粗

GPT-3.5-Turbo、GPT-4、Llama-3-8B 在作者测试问题上均能在两次尝试内生成可执行且命中正确图的查询。论文没有报告问题数量、query exact match、execution accuracy、answer-set accuracy、失败类型或延迟；因此这只能算原型可行性观察，不能视为稳健 NL2SPARQL benchmark。

按类别 precision 的业务含义

所有组合的 C 类 precision 均超过 80%；GPT-4 与 Llama-3-8B 的所有提示组合超过 95%。作者认为高 A/C precision 可以让专家批量接受/拒绝明显案例，把精力留给 B。图 4 中 Llama-3-8B + CoT 的 A precision 约 82.01%，略高于 GPT-4 + CoT 的约 80.48%；但 A/B 区分仍是主要错误源。

不要过度解读：论文没有报告 A/C 自动过滤后的 coverage、错误接受/错误拒绝数量，也没有按真实风险设置阈值。高 precision 只有与预测量、recall 和业务代价同时评估，才能证明能安全减少人工工作。
LIMITATIONS

局限：论文明确承认的，与复核后可推断的

1. 无端到端对照

没有将完整 OntologyRAG 与 vector RAG、人工流程、传统 ontology matcher、BERTMap 或确定性 SPARQL 模板比较。两个 500 条实验分别测试闭卷映射和 label 分类，未形成端到端指标。

2. “Better/Faster” 未直接测量

没有专家任务完成时间、单位映射成本、最终映射 precision/recall、返工率或用户研究。效率提升是由“可过滤 A/C”推导出来的。

3. gold 规模与来源有限

接近度数据由 GPT-3.5 生成后专家修订，只有 500 条且类别不均衡；没有跨机构、跨语言、跨 ontology family 的外部验证。

4. 解释没有被严谨评估

作者仅人工浏览并认为解释质量与等级预测相关；没有专家盲评、事实支持率、反事实一致性或可操作性指标。理由也由预测等级条件化，存在事后合理化。

5. 检索实验缺少规模

只称三个模型在两次内生成正确查询，未给测试集大小和 execution accuracy。无法判断 schema 扩大、复杂组合查询、歧义问题或空结果时的可靠性。

6. 本体“推理”使用较弱

公开流程主要取回已有 mapping edge 与 label；未展示层级蕴含、关系组合、公理约束或逻辑证明用于映射判断。因此证据支持“KG-grounded”，不充分支持“ontology reasoning”。

公开实现暴露的工程风险

代码观察影响生产级修正
SPARQL 与 JSON 生成使用无上限 while 重试。模型持续失败时可能无限调用、失控成本或卡死。最大尝试次数、结构化输出、错误分类、fallback template 与 circuit breaker。
多处使用 Python eval() 解析模型输出。若输入不可信，存在代码执行风险；也容易被非标准 JSON 破坏。JSON schema / Pydantic 严格解析，拒绝额外字段。
sort_mapping_results 以 mapping level 为字典 key。同一等级的多个候选会相互覆盖，摘要前可能每级只剩一个结果。稳定排序列表，不按等级去重；增加回归测试。
remove_lower_mapping_level 的比较实际使用 mapsToLabel 字符串。注释声称保留更高 mapping level，但实现不像是在比较 A/B/C；可能错误去重。显式等级序、按 code + provenance 去重，并保留所有原始候选。
模型与云端点配置固定在 Azure/TGI 适配。论文数值依赖旧模型快照与不可完全重建的托管环境。锁定 model/version、保存 request/response、容器化推理和 deterministic eval。

以上工程观察来自 2026-07-14 对公开 GitHub 主分支的静态复核；它们不一定影响论文中已离线生成的表格数值，但会影响直接把原型用于生产或复现完整在线流程。

OAG IMPLICATIONS

对我们讨论的 OAG，真正可复用的是什么

值得保留的设计

  1. 结构先限定搜索空间：精确 code、数据源和 mapping direction 由图查询决定，避免 embedding 把相似但不对应的概念混在一起。
  2. 自然语言编译为可审计查询：保留 SPARQL 作为中间表示，便于检查 Agent 到底查了什么。
  3. 分类与解释分离：先得到结构化 decision，再生成面向人的理由，优于一次性自由生成。
  4. 把不确定性转成人工队列：B 类是“需要进一步判断”，符合 Agent 负责分流、专家处理边界案例的思路。

必须进一步升级的设计

  1. 从 label pair 升级为 semantic evidence pack：加入定义、同义词、父子类、属性限制、映射 provenance 和反例，而不是只比较两个名称。
  2. 从三档主观等级升级为可操作关系：例如 exact / broader / narrower / related / conflict / no-evidence，并明确方向性。
  3. 把 ontology reasoner 放进判定链：先做可确定的类型/层级/约束检查，再让 LLM 处理剩余语义歧义。
  4. 把解释升级为可验证证明：每个判断引用具体三元组、规则或原始来源，解释与分类分别评估。

从 OAG 需求倒推“可用本体”的质量约束

既然本体治理作为独立模块，OAG 只需声明接口契约。受本文启发，至少需要：

标识与词汇契约

每个概念稳定 ID；首选标签、同义词、定义、语言与版本明确；禁止仅靠显示名称做实体等价。

关系语义契约

mapping relation 必须区分方向、等价/上下位/相关/冲突，并携带来源、版本、有效期和证据。

可查询性契约

提供 machine-readable schema、允许的 query pattern、命名图目录和示例，使 Agent 可生成受约束查询。

推理能力契约

明确哪些蕴含已物化、哪些由 reasoner 计算、采用开放还是闭世界、哪些约束可用于否证。

证据完整性契约

每个候选映射能回溯到原始事实；OAG 返回的子图必须包含判定所需最小充分上下文。

评测接口契约

本体模块提供 competency questions 与 expected bindings；OAG 另外评测 query generation、evidence recall、decision 和 explanation。

建议的复现实验

最小实验矩阵：在同一批真实映射审核样本上比较 ① label-only LLM，② embedding RAG，③ RDF mapping retrieval + label LLM（论文方案），④ RDF + 邻域证据，⑤ RDF + 形式推理 + Agent。统一报告候选 Recall@K、relation macro-F1、A/C 自动处理 coverage@target-risk、专家分钟/条、逐声明证据支持率和端到端成本。
